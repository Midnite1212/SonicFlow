# 0007 — Serve the engine to other Macs on the network

**Status:** accepted · 2026-10-29

## Context

The M4 Max runs parakeet-v2 + qwen3-4b in 133 ms p50 where the M3 Pro laptop takes 378 ms (`docs/LATENCY.md`). Dictating on the laptop through the Mac Studio's engine is faster than its own, but guardrail 4 keeps the engine on loopback, and dictated audio is private (guardrail 3).

## Decision

- Sharing is off by default and turned on per Mac in Settings, which calls `POST /v1/lan` on loopback. The choice is saved in `lan.json` and restored when the engine restarts.
- A second listener on port 8766 serves the same app on every interface. The loopback listener on 8765 is unchanged, so this Mac's own client is unaffected.
- The listener speaks TLS with a self-signed certificate generated by `/usr/bin/openssl`. Clients pin its SHA-256 instead of trusting a CA, so no new dependency is needed and no certificate authority is involved.
- Every request on the listener must carry `Authorization: Bearer <token>`, compared in constant time. The `/v1/lan` controls are refused there, even with the token.
- The pairing code bundles host, port, token and fingerprint into one string to copy. Resetting rotates the token, which unpairs every client. The client keeps the code in the Keychain.
- The client checks the code by calling `/health` before saving it. It dictates through the paired engine whenever that engine is connected and falls back to its own engine otherwise.
- No Bonjour discovery: the user has to visit the sharing Mac for the code anyway, and the code already names the host.

## Consequences

Audio leaves the Mac only for a Mac the user paired, and only encrypted. Anyone holding the code can dictate through the shared engine and manage its models, so the code is treated as a credential. The Studio only helps while both Macs are on the same network; away from it the laptop silently uses its own engine. A dictation in flight when the paired engine drops fails, and the next one falls back.
